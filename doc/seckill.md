# 秒杀设计说明

配套文档:`mall_architecture.md` 3.12(规则口径)、本文(为什么这么设计)。

---

## 1. 一条秒杀从建到结束

**① 建活动(商家后台)**:新建草稿(活动名、起止时间、若干商品项:选 SKU、填秒杀价、配额、每人限购),确认后点「发布」。发布在一个事务里校验并冻结库存,返回"已冻结 N 件" —— 这 N 件从这一刻起普通订单买不到。

**② 到点开始(定时任务,每分钟)**:把到点的活动置为"进行中",并把每个商品项的"还能抢多少"写进 Redis。

**③ 抢购(小程序)**:列表/详情看场次 → 选地址、看实付 → 提交。提交经过三层:接口限流 → Redis 闸门(库存 + 限购)→ 数据库事务(精确校验限购、占配额、切库存、落订单),然后拉起支付。

**④ 支付与未支付**:支付成功就扣实物库存并解除锁定(冻结在下单时已经转走了,这里不参与);15 分钟未支付被关单,则锁定、配额、限购账本、Redis 名额全部退回,名额重新可抢。

**⑤ 结束 / 取消**:到点或商家取消都做同一套收尾 —— 解冻没卖掉的配额、清掉 Redis、状态置终态。已下的未支付单仍可支付(它们占的是锁定,不是冻结)。

---

## 2. 为什么发布就冻结

开抢才冻结的话,活动开始前这批货会被日常订单吃掉,到点就会出现"活动上线但一件都没有"。

冻结做的是 `frozen_stock += 配额`,条件是"划完之后可售不为负";一次发布里的所有商品项在同一个事务里,任一项不够就整次回滚,不会留下半个活动。它**不碰 `stock`**,所以商家盘货的总量、`total_stock` 的汇总口径、退款回库的逻辑都不受影响,变的只是"这部分不卖给普通单"。

代价是活动未开始时这部分库存不可售,后台活动列表直接显示冻结量,商家取消活动即解冻。

## 3. 并发:三层各管一段

| 层 | 承担 | 成本 |
|---|---|---|
| 接口限流 | 同一用户刷接口 | 一次 Redis 计数,10 次/10 秒 |
| Redis 闸门 | 库存 + 限购两道快速判断,超了直接返回 | 一次脚本执行 |
| 数据库事务 | 精确校验、占配额、切库存、落订单 | 只对通过闸门的请求执行 |

热点商品 5 万 QPS、配额 1000 时,数据库大约只看到 1000 笔成功单,**与 QPS 无关**。

限购判断必须放在闸门里而不只是放在数据库:只放数据库会形成"扣 → 查 → 退"的循环 —— 请求被拦下后补偿把名额还回去,然后立刻重来。

限购的真相仍然在数据库:账本一人一行,锁的是"这个人 × 这个商品",不是整件商品,所以不同用户互不阻塞;Redis 的计数只是快,丢 key 时按数据库的值改回来。

补偿挂在事务回滚回调上 —— `@Transactional` 方法返回后才提交,提交失败(约束冲突、连接断开)走不到方法里的 catch。

---

## 4. Redis 不是账本

活动开始时把"配额 − 已占用"写进一个字符串(key 到活动结束后一天自动过期),直接覆盖,所以重复跑、运维手动重跑都没有副作用;只写库存,不写限购。

请求进来发现 key 不存在(Redis 重启、任务没跑到、被手动清空),就用数据库的剩余量补一次;补不上才拒绝。这条兜底保证 Redis 出问题也不会变成"活动下线"。

列表页的"已抢 x%"读数据库快照,详情页的"还剩 N 件"优先读 Redis —— 详情页会被反复刷新,每次都查库等于把秒杀流量压到数据库上。

---

## 5. 需要记住的三条

- **支付与退款不改已占用配额**:它统计的是"已占用的名额"不是"已付款件数",所以那两条路径不必为秒杀开分支。
- **"关单后钱又到账"必须开分支**:关单时已经把冻结退回去了,不重新占回来会让可售变成负数。
- **状态迁移一律用条件更新**:多实例、手动重跑都会重复执行同一段逻辑,受影响行数为 0 就说明别人做过了。
